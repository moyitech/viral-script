# 热榜语义去重模型对比实验与架构决策

## 1. 文档状态

- 实验日期：2026-08-28（Asia/Shanghai）
- 状态：单批次探索实验，结论已进入当前实现
- 决策：使用 `kinfra-text-embedding-4b`，余弦相似度阈值设为 `0.72`
- 适用范围：NewsNow 热榜标题的事件级去重，不用于正文事实核验或离线质量评分

本文记录从 Hy3 直接聚类迁移到文本向量聚类的依据。它保留实验方法、指标、阈值选择逻辑、
局限和生产实现约束，供后续技术报告引用。实验未输出、记录或硬编码任何 API Key。

## 2. 背景与问题

原选题链路把 140 条 NewsNow 热榜标题一次性发送给 Hy3，使用 `no_think` 模式返回事件簇，
再从去重结果中选择最多 40 个事件，并发调用 4 次 Hy3 `high`，每次生成 5 个选题。实测中，
单次 Hy3 去重约需 113 秒，成为 20 个推荐的主要延迟来源。

本实验回答三个问题：

1. embedding 加本地余弦聚类能否近似 Hy3 的事件划分？
2. `kinfra-text-embedding-0.6b` 与 `kinfra-text-embedding-4b` 的差异是否足以影响选型？
3. 在使用连通分量聚类时，两个模型分别应采用什么阈值？

## 3. 实验设置

### 3.1 输入数据

同一冻结批次包含 140 条 NewsNow 标题，来自当前默认的 7 个公开热榜源，每个来源最多取前
20 条：微博、百度、知乎、抖音、B 站、今日头条和澎湃新闻。条目按“各来源第 1 名、各来源
第 2 名……”交错排列，以避免单个平台连续占据输入前部。

140 条标题共产生：

\[
\binom{140}{2}=9,730
\]

个无序标题对。

### 3.2 对比方法

- 伪参考：Hy3 `no_think` 事件聚类。它输出 101 个事件，其中 14 个为多标题事件簇，最大簇
  包含 18 条标题。转换为成对标签后，共有 190 个“同一事件”正例对。
- 候选 A：`kinfra-text-embedding-0.6b`，向量维度 1,024。
- 候选 B：`kinfra-text-embedding-4b`，向量维度 2,560。
- embedding 请求与 Hy3 复用 `hyscript.config.settings` 中的 TokenHub 地址和密钥。
- TokenHub 请求显式使用 `encoding_format="float"`；省略该参数会返回 HTTP 400。
- 每个模型只请求一次 140 条标题的 embedding。向量按响应 `index` 恢复输入顺序并检查数量、
  索引集合和维度一致性。

Hy3 结果只是伪标签，不是人工真值。因此本文中的 precision、recall 和 F1 表示“与本次 Hy3
划分的一致程度”，不能解释为客观事件真值准确率。

## 4. 聚类与阈值选择

先对每个向量做 L2 归一化，再计算所有标题对的余弦相似度。相似度大于等于候选阈值时，在
两个标题之间建立无向边；最终事件簇是该图的连通分量。这个定义具有传递性：即使 A 与 C
没有直接越过阈值，只要 A—B 和 B—C 均越过阈值，三者仍属于同一事件簇。

阈值搜索与生产聚类使用同一连通分量语义：

1. 在 `0.30` 至 `0.99` 上以 `0.01` 为步长粗搜；
2. 在粗搜最优点前后 `0.02` 的区间内以 `0.0005` 为步长细搜；
3. 将连通分量重新展开为 9,730 个成对预测，与 Hy3 伪标签计算 precision、recall、F1；
4. 优先选择 F1 最高的阈值；若并列，依次选择 precision 更高、阈值更高的结果；
5. 同时记录细搜离散网格中 F1 不低于最优值 99% 的采样点，并报告这些点的最小、最大阈值；
   表中的范围不是连续置信区间，也不表示两端之间每个实数阈值都满足条件。

实验也计算了“不做传递闭包、只看直接相似度边”的最优阈值。该数字仅用于诊断，不能直接
用于当前生产算法，因为直接边阈值和连通分量阈值优化的是不同决策对象。

## 5. 实验结果

| 方法 | 维度 | 远端调用 | 本地分析 | 实验最优连通分量阈值 | Precision | Recall | F1 | 事件数 | 重复簇 | 最大簇 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| Hy3 `no_think` 伪参考 | — | 113.10 s | — | — | — | — | — | 101 | 14 | 18 |
| `kinfra-text-embedding-0.6b` | 1,024 | 3.16 s | 2.32 s | 0.6105 | 0.7652 | 0.9947 | 0.8650 | 99 | 12 | 21 |
| `kinfra-text-embedding-4b` | 2,560 | 9.85 s | 2.76 s | 0.7200 | 0.8349 | 0.9579 | 0.8922 | 103 | 12 | 20 |

补充阈值结果：

| 模型 | 最优连通分量阈值 | 99%-of-best F1 区间 | 最优直接边阈值 |
|---|---:|---:|---:|
| `kinfra-text-embedding-0.6b` | 0.6105 | 0.6065–0.6300 | 0.5527 |
| `kinfra-text-embedding-4b` | 0.7200 | 0.7190–0.7225 | 0.5653 |

4B 相比 0.6B 的 F1 高 `0.0272`，precision 高 `0.0697`，recall 低 `0.0368`。选题去重中，
错误合并两个不同事件会同时丢失候选多样性和来源边界，因此更高 precision 比追求接近 1 的
recall 更符合当前产品风险偏好。0.6B 的 99 个事件与 4B 的 103 个事件都和 Hy3 的 101 个相差
2，事件总数不能作为两者之间的选型依据。

只比较远端调用，4B 的 9.85 秒约为 Hy3 113.10 秒的 1/11.5。4B 的 2.76 秒本地分析包含多轮
阈值搜索和指标计算，与 Hy3 的远端调用不是同口径，不能相加后声称生产链路提速倍数。生产
只执行一次固定阈值聚类，但本实验没有单独测量这一步及完整 20 条推荐的端到端延迟，也没有
记录两种 embedding 的价格、配额和吞吐上限，因此不能仅凭本次计时判断线上成本收益。

## 6. 差异分析

在各自推荐的连通分量阈值下，把每个标题对的直接相似度边判定进行比较，两个 embedding 模型
在全部 9,730 个标题对上的一致率为 99.54%，但该数字被大量“不同事件”负例抬高。只看任一
模型判为正边的标题对，正例 Jaccard 为 0.698，说明模型间仍有值得关注的聚类边界差异。这两
个一致性数字比较的是直接边，不是经过传递闭包后的最终簇成员关系。

抽查分歧样本后，主要争议集中在“同一个大事件的不同进展或不同切面”：Hy3 有时把它们合成
一个事件，embedding 有时按具体进展拆开；反方向也存在。这个现象说明“同一事件”不是完全
客观的标签，后续人工标注必须明确时间跨度和事件粒度，不能只让标注者凭直觉判断。

## 7. 架构决策

当前生产链路采用以下流程：

```text
NewsNow 最多 140 条标题
  -> kinfra-text-embedding-4b 一次批量 embedding
  -> L2 归一化 + 余弦相似度 >= 0.72 建边
  -> 本地 connected components 事件聚类
  -> 按跨来源数量与热榜排名选择最多 40 个事件
  -> 4 个 Hy3 high 请求并发生成，每批 5 个选题
  -> 恰好 20 个待核验推荐
```

实现约束如下：

- embedding 和 Hy3 chat 复用同一个异步 `AsyncHy3Client` 与连接池；
- 本地 O(n²d) 聚类通过 `asyncio.to_thread` 执行，不阻塞 API 的事件循环；
- 每个连通分量保留全部原标题、平台、排名、条目 ID 和 URL，不让向量去重破坏 lineage；
- 生成请求继续使用 Hy3 `high`，不设置 `max_tokens`；
- 默认并发为 4，每个失败批次最多单独重试一次；
- 输出分别记录 embedding 请求数、Hy3 chat 请求数、模型名和阈值；
- 配置入口为 `TOPIC_EMBEDDING_MODEL`、`TOPIC_SIMILARITY_THRESHOLD` 和
  `TOPIC_MAX_GENERATION_CONCURRENCY`。

成功且无需重试的默认运行包含 1 次 embedding 和 4 次 Hy3 chat，共 5 次远端请求。SDK 的
自动重试被设为 0，embedding 在 Application 层也不重试；4 个生成批次各最多尝试 2 次，因而
一次最终成功的运行可能包含 4–8 次 chat。任一批次在一次重试后仍失败时，TopicAgent 抛出
`TopicGenerationError`，不返回不足 20 条的部分结果。因此“恰好 20 个”是成功返回值的契约，
不是外部服务持续失败时仍能满足的可用性保证。

生成调用方不传 `max_tokens`，长度上限由当前 Endpoint 默认值决定；代码只校验返回 JSON 和
推荐数量。后续成本报告需要另行记录服务端实际 usage 与截断情况，不能把“不设置”解释为
无限输出或固定成本。

选择 `0.72` 而不是更精细的 `0.7200` 之外数字，是因为它正好是本批次最优点，也位于很窄的
99%-of-best 区间内，便于配置、解释和后续版本比较。

需要区分“阈值选择”和“模型选择”：每个模型的阈值按普通 F1 选择，4B 模型则因同时获得更高
F1 与更高 precision 而被采用，并在产品判断中偏向减少误合并。当前实验没有把误合并成本写入
加权损失函数，也没有设 precision 下限，因此这是一个有明确工程偏好的暂定决策，不是已经由
成本敏感指标证明的全局最优选择。

## 8. 局限与有效性威胁

1. 只有一个日期、一个 140 条批次，无法覆盖不同日期、突发大事件或不同来源组合。
2. Hy3 是伪参考且自身可能过度合并或过度拆分；当前结果衡量的是近似 Hy3，不是人工真值。
3. 阈值在用于评估的同一批数据上选择，存在过拟合，F1 不应作为泛化性能直接引用。
4. 标题很短，歧义、缩写和上下文缺失会影响 embedding；本阶段没有读取新闻正文。
5. 连通分量可能产生链式合并，单条“桥接标题”可能把两个本应分开的簇连接起来。
6. API 延迟受服务负载与网络影响；本次单次计时没有误差范围。
7. 本次仅保留了汇总指标，没有把原始热榜标题、Hy3 原始响应和 embedding 向量提交到仓库，
   因而无法对这一次动态热榜做逐标题完全重放。
8. 成对 F1 会放大大簇对总分的影响，当前没有簇级指标或按“误合并比漏合并更昂贵”加权的
   指标；precision 偏好是产品判断，不是由当前 F1 目标函数自动表达的。
9. 本次未冻结 Hy3 伪参考的完整 prompt、采样参数、解析版本、服务端模型版本、依赖环境和
   精确热榜获取时间；即使重新得到相同标题，也不能保证生成完全相同的伪标签。
10. “同一事件”的允许时间跨度和进展粒度没有形成标注规范，分歧分析只能作为定性观察。
11. 当前生产聚类没有最大簇限制或桥接边复核，链式合并风险仅由较高阈值缓解。
12. 生成端不传 `max_tokens` 是当前明确策略，但 Endpoint 默认上限没有被版本化；默认值变化
    可能造成输出长度、截断率与成本漂移，运行轨迹后续应记录实际 usage 和 Endpoint 配置。

## 9. 复现实验注意事项

后续复跑应使用显式 opt-in 的实验脚本，并遵守以下顺序：

1. 通过 `hyscript.config.settings` 加载 TokenHub 与 NewsNow 配置，禁止打印密钥；
2. 获取 NewsNow 后立即冻结标准化标题、来源、排名、URL、获取时间和内容哈希；
3. 对同一标题顺序分别请求 Hy3 伪参考、0.6B 和 4B embedding，每种方法只调用一次；
4. 原样保存模型名、向量维度、响应索引、调用耗时、阈值搜索网格和原始簇；
5. 将原始快照和汇总指标分开保存，并为输入快照计算 SHA-256；
6. 不把该实验加入默认单元测试；单元测试继续使用 fake client。

TokenHub embedding 的必要请求字段为：

```python
response = await client.embeddings.create(
    model="kinfra-text-embedding-4b",
    input=titles,
    encoding_format="float",
)
```

本次用于探索的临时脚本未作为生产模块提交。正式复现实验脚本应单独放入 `scripts/`，输出到
不包含凭证的实验目录，并在技术报告中引用输入快照哈希，而不是依赖动态热榜仍保持不变。

## 10. 后续验证计划

- 在至少 7 个不同日期保存独立快照，覆盖普通日和突发热点日；
- 建立分层人工标注集，明确“同一大事件的不同进展”是否合并；
- 在不重新调阈值的前提下验证 0.72，并报告 macro/micro F1、簇级误差和事件数量偏差；
- 单独审查最大簇、跨平台簇和链式合并簇，记录误合并造成的选题损失；
- 比较固定 0.72、按日期校准阈值以及限制最大簇/桥接边的方案；
- 记录 embedding 远端延迟、固定阈值本地聚类延迟、端到端选题延迟及失败率的分布；
- 若多日人工真值显示 4B 优势不稳定，再重新评估 0.6B 的成本收益。
